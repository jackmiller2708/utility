  - `packages/toolkit` (`@utility/toolkit`): Generic `Tool`, `Operation`, and `ToolRegistry` interfaces and registry layer.

  - `packages/pdf` (`@utility/pdf`): Poppler adapter architecture and interface foundation for M2.

### 2. Capabilities & Architecture

- **Runtime Services (`@utility/runtime`)**:
  - `FileSystem`: Typed Effect filesystem operations (`read`, `write`, `copy`, `move`, `stat`, `remove`, `exists`).
  - `WorkspaceManager`: Ephemeral sandboxes per operation (`input/`, `temp/`, `output/`) with path traversal guards and automatic cleanup.
  - `Process`: Controlled binary spawning using argument arrays (never executing shell strings).
  - `ArtifactStore`: Artifact registration, SHA-256 calculation, metadata persistence (`~/.utility/artifacts`), and secure path lookup.
- **Image Adapter (`@utility/image`)**:
  - `SharpImageServiceLive`: Handles resize, aspect ratios (`inside`, `cover`, `contain`, `fill`, `outside`), format conversions (`webp`, `jpeg`, `png`, `avif`), and metadata extraction.
- **Security & Device Auth (`apps/utility-api`)**:
  - `DeviceAuthGuard` & `DeviceAuthService`: Auto-authorizes localhost development traffic (`127.0.0.1`, `localhost`) while supporting cryptographic device signature verification (`x-device-id`, `x-timestamp`, `x-nonce`, `x-signature`) for remote/LAN requests.
- **Angular Client (`apps/utility-web`)**:
  - Drag-and-drop file upload with live preview and dimension/size inspector.
  - Granular resize controls: target width/height, quick scaling presets (50%, 25%, 1080p, square), fit modes, output format selector, and upscale toggles.
  - Result view: side-by-side comparison, file size reduction percentage, SHA-256 fingerprint, and one-click artifact download.

## M2 Implementation Summary (PDF Backend)

Poppler-backed PDF operations are implemented end-to-end and reachable over HTTP, following the exact same `Tool`/`Operation`/`ToolRegistry` pattern `image.resize` established in M0 — no new controller code was needed; they ride the existing generic `POST /api/v1/tools/:operationId` route.

- **`packages/pdf`**:
  - `PdfService` (`PopplerPdfServiceLive`): shells out to `pdfinfo`, `pdftoppm -png`, and `pdfimages -png` (all via the sandboxed `Process` service — argument arrays only, never shell strings). Requires `Process` and `FileSystem`.
  - `inspect`: page count, and title/author when present in the PDF's metadata.
  - `renderPages`: renders every page (or a `firstPage`–`lastPage` range) to PNG at a configurable DPI (default 150); lists the workspace output directory to collect the rendered files.
  - `extractImages`: extracts every embedded raster image to PNG; returns an empty list (not an error) when a PDF has none.
  - `InvalidPdfError` / `PdfProcessingError` (`errors.ts`): a malformed/non-PDF input is distinguished from an operational failure by sniffing Poppler's stderr, and maps to `400 Bad Request` in the API (see `effect-runtime.service.ts`).
  - `tool.ts`: `pdfTool` (category `"Document"`) registers `pdf.inspect`, `pdf.render-pages` (params: `dpi`, `firstPage`, `lastPage`), and `pdf.extract-images`. Both multi-output operations save one `Artifact` per page/image via the existing `ArtifactStore`, so they download through the existing `/api/v1/artifacts/:id/download` route unchanged.
- **`packages/protocol/src/pdf.ts`**: `PdfInspectInput/Output`, `PdfRenderPagesInput/Output`, `PdfExtractImagesInput/Output` — the render/extract outputs carry `pages: Artifact[]` / `images: Artifact[]`.
- **`apps/utility-api`**: `pdfTool` + `PopplerPdfServiceLive` registered in `AppLive` alongside the image layer; `@utility/pdf` added as a dependency.
- **System requirement**: `poppler-utils` (`pdfinfo`, `pdftoppm`, `pdfimages`) must be installed on the host — same category of dependency as Sharp is for image, just a system package instead of an npm one.

## M2 Implementation Summary (Merge & Split Backend)

Added after the PDF Documents UI shipped, completing the roadmap's M2 `merge/split` item.

- **`packages/pdf/src/service.ts`**: `splitRanges` (Ghostscript `gs -sDEVICE=pdfwrite -dFirstPage=X -dLastPage=Y`, one invocation per range, run sequentially) and `merge` (`pdfunite in1 in2 ... out.pdf`). Both real-file-verified: a 13-page extract from a live 110-page/96MB document, and a 3-page merge across two files in a **user-reordered** sequence (drag-to-reorder in the UI, confirmed by checking the merged page count matched the reordered, not upload, order).
- **`isMalformedPdfStderr`** (shared with inspect/render/extract) extended to recognize Ghostscript's own malformed-input phrasing (`Unrecoverable error`, `stackunderflow`, `trailer dictionary`) alongside Poppler's, verified against Ghostscript's real stderr output on a non-PDF input.
- **New system requirement**: Ghostscript (`gs`) — confirmed present on this host, not previously a project dependency.
- **`packages/pdf/src/tool.ts`**: a second tool, `pdfMergeSplitTool` (id `pdf-merge-split`, category `"Document"`), separate from `pdfTool` — registers `pdf.merge` and `pdf.split` as their own sidebar-level tool rather than folding them into `PDF Documents`, since merge's multi-file input doesn't fit that tool's single-file screen.
- **`apps/utility-api/src/tools/tools.controller.ts`**: unlike inspect/render/extract, merge and split needed **dedicated routes** (declared before the generic `:operationId` catch-all, since Express matches route registration order) — `pdf.merge` uses `FilesInterceptor('files')` for true multi-file upload (the generic route only supports one `file` field), and `pdf.split` uses `FileInterceptor('file')` plus a `ranges` form field sent as a JSON string (`[{firstPage,lastPage}, ...]`) and parsed server-side, since multipart form-data can't carry structured arrays natively.
- **`apps/utility-web`**: new `document/merge-split` module. New reusable pieces: `SortableFileListComponent` (native HTML5 drag-and-drop reorder, no library), a `grip` icon added to `IconComponent`, and `DropzoneComponent` extended (additively — existing single-file consumers unchanged) with a `multiple` input/`filesSelected` output and a `showPasteHint` toggle. `GalleryGridComponent` now hides "Download All" when there's exactly one result (merge always produces one file — the button was redundant chrome for that case).

## M3 Implementation Summary (Jobs Backend)

Generic — works for any registered operation (`image.resize` included), not special-cased to PDF, per the scope decision going in.

- **`packages/toolkit/src/job.ts`**: `JobRegistry` service (in-memory `Map`, `Layer.sync`) with `pending → running → completed | failed | cancelled` status, real progress (`{completed, total, message}`), and `cancelJob` (interrupts the job's stored `Fiber`). `trackJob(registry, jobId, effect)` wraps any operation's effect so its outcome updates the registry automatically — built on `Effect.onExit`, not `Effect.exit`: a first version sequenced the status-update code *after* awaiting the exit, which is wrong, because interrupting a fiber tears down every remaining step in it, including code placed after an awaited exit — the interrupted job's own "mark cancelled" call was itself getting interrupted before it could run, silently leaving jobs stuck at `"running"` forever. `Effect.onExit`'s finalizer is guaranteed to run, and to run uninterruptibly, which fixes this; caught by a dedicated test that interrupts a real fiber and asserts the final status.
- **`OperationContext`** (`packages/toolkit/src/operation.ts`) gained an optional `reportProgress`, present only when running as a job. Every existing operation still works unchanged when it's absent (undefined) — this is additive, not a breaking change to the M0–M2 operations.
- **`packages/pdf/src/service.ts`**: `renderPages`/`extractImages`/`splitRanges` accept an optional progress callback. When present, `renderPages`/`extractImages` switch from one batched Poppler invocation to fixed 10-page chunks, reporting progress after each. This is **not** a cosmetic detail — verified empirically before implementing:
  - `pdftoppm` names output by real page number, so a shared prefix across chunked invocations never collides.
  - `pdfimages` restarts its own counter at `-000` on *every* invocation — a naive chunked implementation using one shared prefix would have each chunk silently overwrite the previous one's files. Fixed with a zero-padded, chunk-unique prefix; a dedicated test builds a PDF with one embedded image per page across multiple chunks and asserts all of them survive.
  - The non-progress (synchronous route) code path is untouched — chunking only activates when a job actually requests progress, so M2's already-verified performance characteristics don't change.
  - `splitRanges` reports progress per range (it already looped one `gs` call per range); `merge` stays coarse (`pdfunite` has no per-file granularity to report).
- **Real bug found and fixed while live-testing cancellation, not by inspection**: `Process.spawn` (`packages/runtime/src/process.ts`) used `Effect.async` without registering an interrupt handler. Cancelling a job correctly stopped the *Effect* from waiting on the result and marked the job `"cancelled"` — but the underlying OS process (`pdftoppm`, `gs`, `pdfunite`, `pdfimages`, and Sharp's own child processes if any) kept running to completion in the background, unkilled, writing into a workspace that was already torn down. Confirmed live: submitted a real 600 DPI render against the 96MB document, watched `pdftoppm` running via `ps`, cancelled the job, and the process was still alive. Fixed by returning a cleanup `Effect.sync(() => proc?.kill("SIGKILL"))` from the `Effect.async` registration — Effect runs this automatically, and only, on interruption. Reverified the same way: process is confirmed gone within ~1s of cancelling, workspace confirmed cleaned up. This fix benefits every operation that shells out, not just the async path — the old code had the same latent gap for any future synchronous timeout/interruption too.
- **`apps/utility-api/src/jobs/`**: `JobsController` — `POST /api/v1/jobs/:operationId` (generic for *any* operation, `AnyFilesInterceptor` so both single- and multi-file operations work through one route), `GET /api/v1/jobs/:id`, `GET /api/v1/jobs`, `DELETE /api/v1/jobs/:id`. Input is built generically from the operation's own declared `parameters`: the parameter with `type: "file"` decides whether uploaded file(s) become a single filename or an array (matching the `file` vs `files` naming already used by every operation), and every other parameter is coerced from its raw multipart string per its declared `type` (`number`, `boolean`, or `string` — a `string` field holding JSON, like `pdf.split`'s `ranges`, is parsed automatically). No per-operation controller code was added for this route, unlike the synchronous `pdf.merge`/`pdf.split` routes, which still needed dedicated handling.
- **Known, accepted limitation**: a cancel request arriving in the small window between a job's fiber being forked and its reference being attached to the registry (single-digit milliseconds) reports "not cancellable yet" rather than cancelling. Deliberate trade-off for an in-memory MVP job engine, not a silent gap — documented here rather than engineered around.

## M3 Implementation Summary (Jobs UI)

Wires both M2 workbenches to the M3 jobs backend, replacing each screen's single blocking request + client-side elapsed-time counter with real submit/poll/cancel.

- **`apps/utility-web/src/app/core/services/job-tracker.service.ts`** (new): the app-wide job ledger. `submit$()` registers a job the moment submission succeeds and returns the same observable so callers still handle their own success/error UI; polls `GET /jobs` every 900ms while any job is active and stops automatically once none are. Exposes the live list to both the footer tray (every job, every tool) and each workbench's own inline progress (filtered by id). Dismissing a finished ticket is tracked locally (`_dismissedIds`), since `GET /jobs` returns the server's full authoritative history with no delete-from-history concept.
- **`apps/utility-web/src/app/domain/models/job.model.ts`** (new): `JobModel` (`isActive`/`isTerminal` derived from status) plus `JobModelFromJobResponse`/`JobModelsFromJobListResponse` adapters.
- **Footer job tray** (`ui/organisms/job-tray`, `ui/molecules/job-ticket`, new): expanded by default in the app footer so progress is visible without a click. Each ticket shows the job's real ledger (`completed / total — message` when the backend reports it, otherwise a bare running/queued state), a cancel control while active, a dismiss control once terminal. Motion is fully choreographed per DESIGN.md's job-lifecycle patterns — Stamped In on arrival, Odometer Tick on every progress increment, Pulled Sheet on completion, Misregistration on failure, Pulled Away plays out before the tracker actually drops a dismissed or completed ticket so the remaining tickets reflow instead of jumping.
- **The route curtain** (`core/services/route-curtain.service.ts`, `core/services/motion.service.ts`, `core/guards/curtain-ready.guard.ts`, `ui/organisms/route-curtain`, new): a full-viewport overlay gating every tool-to-tool navigation behind full opacity before the destination component is even created — the `canActivate` guard doesn't resolve until the curtain is provably opaque, so the swap always happens behind a fully opaque curtain, never mid-fade. Fixes a "flash of black, then fade in" defect from two earlier approaches: Angular's native View Transitions threw `InvalidStateError` against SSR hydration on every navigation, and a plain per-page CSS fade-in left the outgoing dark canvas visible through the transition. Given a minimum-hold buffer this session (320ms, 120ms under reduced motion) after testing showed a warm local navigation could settle and lift the curtain before the fade-in even finished, reading as a flicker rather than a real transition — timed from the moment the curtain reaches opacity, so it only pads fast navigations and never delays a slow one. Verified live: instrumented the curtain element with a `MutationObserver` while driving the Angular router directly, confirmed opacity reached 1 at +173ms, held until +493ms (the configured 320ms hold), and finished fading out at +706ms.
- **`PdfWorkbenchService`** (render/extract): `executeRenderPages()`/`executeExtractImages()` now submit through `JobTrackerService.submit$()` instead of blocking on the operation's own response; an `activeJob` computed tracks the submitted job by id, `cancelActiveJob()` cancels it. `GalleryGridComponent`'s loading state takes an optional `job` input — when set, it shows the job's real `completed/total` ledger and a cancel button instead of a generic elapsed-time message.
- **`MergeSplitService`** (split/merge, converted this session): the same pattern as `PdfWorkbenchService` — `executeSplit()`/`executeMerge()` submit via `JobTrackerService.submit$()` (new `ApiClientService.submitSplitJob$()`/`submitMergeJob$()`, posted to the generic `/jobs/pdf.split`/`/jobs/pdf.merge` routes, replacing the old blocking `splitPdf$`/`mergePdfs$`), `activeJob`/`cancelActiveJob()` mirror the workbench service. Split gets real per-range progress (the backend already reports progress per `gs` invocation); merge stays a coarse pending→running→done since `pdfunite` has no per-file granularity to report, which the ticket's existing "RUNNING…" fallback already handles with no special-casing needed. Cleanup in the same pass: `MergeSplitService`'s elapsed-timer plumbing (`_elapsedSeconds`, `_startElapsedTimer`, `_stopElapsedTimer`, `formatSeconds`) and `GalleryGridComponent`'s now-fully-dead `elapsedLabel` input and fallback branch were removed — nothing else referenced them.
- **`ImageResizeService`** deliberately untouched — `image.resize` stays synchronous. It's fast enough that a job round-trip would add latency without a real progress signal to show for it.

## M4 Implementation Summary (Client Refinement)

Five roadmap items, all in `apps/utility-web` — no new backend surface except Recent Artifacts' pagination, noted below.

- **Tool discovery**: `SidebarComponent` groups tools under their existing `category` field (Media/Document) as section headers instead of a same-row badge; each tool's operations reveal on hover ("Inspect · Render Pages · Extract Images"). Required fixing the domain layer first — `ToolModel`/`ToolParameterModel` were a stale, lossy subset of the backend's real `ToolParameter` schema (missing `label`, `options`, `min`, `max`), and `RuntimeStatusService` wasn't even running the fetched tools list through the project's own DTO→domain adapter convention. Both fixed; `ToolModelsFromToolsListResponse` is the real adapter now.
- **Reusable operation forms**: new `OperationFormComponent`, generic and driven entirely by an operation's `ToolParameter[]` (label/type/options/min/max → Input/Select/Toggle/TileGroup). Deliberately **not** retrofitted onto the three existing hand-built forms (Image Resize, PDF Documents, Merge & Split) — each carries bespoke logic (aspect-ratio locking, DPI/page-range presets, cost estimates, dynamic range rows) a generic renderer can't reproduce without regressing real functionality. Its first real consumer is batch mode's shared settings panel — a genuinely new surface, not a replacement.
- **Drag/drop**: `DropzoneComponent`'s `window:drop` handler previously only reset the "inviting" visual state — a drop anywhere outside the dropzone's own rect did nothing but let the browser navigate to the dropped file. It now `preventDefault()`s and actually captures the files, so a near-miss drop anywhere on the active tool's page still lands (the element-level `onDrop` calls `stopPropagation()` so a precise drop on the plate itself isn't double-handled).
- **Batch operations**: `JobTrackerService.submitBatch$()` submits N independent jobs (one per file) under one client-generated `batchId`; the footer tray's new `BatchTicketComponent` collapses them into one card ("Resize Image ×10 — 6/10 done") that expands to the real per-file `JobTicketComponent`s, each still individually cancellable. Shipped for:
  - **Image Resize** (flagship): SINGLE/BATCH mode toggle, multi-file dropzone + sortable list, `OperationFormComponent`-driven settings, results in `GalleryGridComponent`.
  - **PDF Documents** (retrofit): the same toggle, plus an operation picker (Inspect / Render Pages / Extract Images — the same three the sidebar reveals). DPI stays a curated tile group (an absolute quality tier, reused directly rather than genericized); page range falls through to the generic form once its single-file high-DPI auto-nudge heuristic doesn't apply across N unrelated files. Inspect's batch result has no artifact at all (`{pages, title, author}`, not a file) — it gets its own ledger list rather than being forced into the artifact-grid component; render-pages/extract-images each produce an *array* of artifacts per job, correctly flattened (2 files × 2 pages = 4 results, not 2).
  - **Excluded, on purpose**: `pdf.split` (its one real parameter is page-numbers relative to *one* document's structure — meaningless applied identically across N unrelated PDFs) and `pdf.merge` (multiple files already *is* its one job's own contract, not a batch of independent jobs).
  - **Hardened** after review raised it: `SortableFileListComponent` (shared by all three file-list flows, Merge & Split included) caps its rows at a scrollable 280px instead of pushing settings and the submit button off-screen, and gained a "N FILES · CLEAR ALL" header. Every batch-capable service caps at 25 files — bounds concurrent server-side jobs (each spawns its own Sharp/Poppler process), not just UI tidiness — truncating gracefully with a stated count rather than rejecting the whole drop.
- **Recent artifacts**: new `/recent` route and sidebar entry. Shipped first as a flat list over the entire `GET /artifacts` history; hardened once real usage (691 artifacts had accumulated by the time this was revisited) made the gap concrete. `GET /artifacts` is now cursor-paginated server-side (30/page via `limit`/`cursor`) with server-side search (`q`, case-insensitive substring on name) and operation filtering (`operation`, exact match on `metadata.operation`) — `ArtifactStore.listArtifacts()` in `packages/runtime` does the filtering, pagination, and `total` count in one pass, the count falling out of locating the page rather than costing a second scan. The frontend debounces search input (300ms, `distinctUntilChanged` so resettling on the same query doesn't re-fetch) and sources its operation filter tiles from the same tool registry the sidebar discovers tools from, so the filter can never list an operation that doesn't actually exist.

- **No defined next milestone** — M0 through M4 are all complete; nothing is currently scoped beyond this.
- Nothing left unbuilt from the M3 roadmap item on either half: backend (`async execution`, `progress`, `cancellation`, `in-memory job registry`) and UI (both M2 screens submit jobs, poll for real progress, and cancel through the shared footer job tray) are shipped and tested, including against the real large document that originally motivated M3.
